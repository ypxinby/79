## 1. 当前结论

这是一个 TI CCS / MSPM0G3507 小车工程。当前主线已经从旧开环底层切换为：

```text

→ CarController 统一仲裁
```

## 2. 分层设计

### 2.1 主控制链

```text
MissionLibrary
  静态任务数组、动作参数、开发/比赛任务注册表
        ↓
MissionManager
  选择任务、推进 action_index、重试、暂停、外部冻结
        ↓
MotionAction
  把一个动作的开始/运行/完成/超时转换为统一语义
        ↓
CarController
  唯一正常运动仲裁点，决定当前 run_mode 和左右 normalized 目标
        ↓
LineController / HeadingControl / 定距状态机
  生成本周期左右命令
        ↓
MotorControl
  normalized → cm/s，执行左右轮 PI + 前馈
        ↓
Motor
  最终方向 GPIO、TIMG8 PWM 和强制停车
```

反馈链：

```text
编码器 GPIO ISR
→ Encoder 有符号 delta
→ WheelSpeedEstimator 唯一读清 delta
→ 左右轮速、左右累计距离、中心累计距离
→ MotorControl 轮速反馈
→ 定距动作的 travelled / remaining
```

### 2.2 安全链

```text
K2 长按软件急停
/ 软件 heartbeat watchdog
/ ObstacleSafety
/ 编码器估算器错误
/ MotorControl 错误或目标刷新超时
/ IMU 无效
/ 动作超时
→ 阻止普通目标
→ MotorControl_Stop / Motor_Stop
→ PWM 强制低
→ 急停、watchdog 或 Fault 同时调用 Magnet_ForceOff
→ 必要时 Fault 锁存并让 Mission 进入 ERROR
```

### 2.3 必须保持的边界

- `MissionLibrary` 只描述“做什么”，不直接控制电机。
- `MotionAction` 管理动作语义，不直接调用 `Motor_SetSpeed()`。
- `CarController` 是唯一正常运动仲裁点；普通业务只能在这里提交左右 normalized 目标。
- 启用 P4 后，正常运动最终只由 `MotorControl` 调用 `Motor_SetSpeed()`。
- `Encoder_GetAndClearPulseDeltas()` 只能由 `WheelSpeedEstimator_Update()` 消费，不能让 OLED、定距动作或其他模块再次读清。
- 编码器 ISR 只做边沿判向、计数和溢出标记，不放浮点、滤波、任务逻辑或打印。
- `ObstacleSafety`、急停和 watchdog 的优先级高于所有普通动作。
- `Debug/ti_msp_dl_config.*` 是 SysConfig 生成物；硬件配置应修改 `empty.syscfg`，不要手改生成文件。

## 4. 初始化与调度

### 4.1 启动顺序

```text
SYSCFG_DL_init()
→ App_Init()
→ BluetoothUart_Init()不执行          FEATURE_BLUETOOTH_UART=0
→ VisionReceiver / VisionTuning / VisionUart 初始化
→ SysTick_Config(10 kHz)
→ 使能编码器 GPIO 中断
→ 进入主循环
```

`App_Init()` 内的关键顺序：

```text
Magnet_Init，先将 PB5 拉低，确保继电器释放
→ Fault / EmergencyStop / Watchdog / RuntimeSnapshot
→ Motor_Init，并先保持输出为低
→ Encoder_Reset
→ AppConfig_InitDefault
→ WheelSpeedEstimator_Init
→ MotorControl_Init
→ IMU 初始化、200 次 bias 校准、Yaw 清零
→ HeadingControl / CarState / Menu / Mission
→ Track / Ultrasonic / Obstacle / Servo / CarController / Key / OLED
→ Motor_Stop
```

车辆上电时应保持静止，让 IMU 完成 gyro bias 校准。

### 4.2 100 us SysTick

当前 SysTick 为 10 kHz：

```text
每 100 us：
  Servo_Tick100us()
  Ultrasonic_Tick100us()

每 1 ms：
  系统时间 +1
  软件 heartbeat watchdog ISR 检查

每 20 ms：
  只增加 App pending，不在 ISR 内执行完整控制
```

由于 `FEATURE_HW_MOTOR_PWM=1`，`Motor_PwmTick100us()` 不会执行；电机 PWM 由 TIMG8 硬件持续产生。

云台 5 ms / 10 ms pending 链在 `FEATURE_GIMBAL_MOTION_CONTROL=0` 时不编译进当前运行路径。

### 4.3 主循环和真实 elapsed

主循环会合并积压的 20 ms pending，只执行一次 `App_Update_20ms(elapsed_ms)`，并记录 missed、drop、overrun 和 dt clamp。控制 elapsed 最大限制为 100 ms。

当前 `App_Update_20ms()` 顺序：

```text
1.  WheelSpeedEstimator_Update(elapsed_ms)
2.  Watchdog 故障应用
3.  Imu_Update(elapsed_ms)
4.  Ultrasonic_Update_20ms()
5.  ObstacleMonitor_Update_20ms()
6.  舵机保持前向 SV 角度
7.  Key_Update_20ms() + Menu_HandleKeyEvent()
8.  再检查急停和 watchdog；命中则立即停车并提前返回
9.  MissionManager_Update_20ms(elapsed_ms)
10. ObstacleSafety_Update_20ms()
11. ObstacleAvoidance_Update_20ms(elapsed_ms)
12. CarController_Update_20ms(elapsed_ms)
13. MotorControl_Update(elapsed_ms)
14. RuntimeSnapshot / DebugTelemetry / OLED
```

顺序上的关键点：

- 先更新编码器估算，再运行本周期控制器。
- `CarController` 先提交目标，`MotorControl` 后执行轮速闭环。
- 安全链位于最终输出之前。
- OLED 在控制完成后读取状态，不拥有控制权。

视觉 UART 的字节处理在主循环中持续执行，不属于 20 ms 小车动作链。

## 5. 新底层：PWM、编码器和双轮轮速闭环

### 5.1 命令单位

上层统一使用有符号 normalized 命令：

```text
-1000 ～ +1000
```

启用 P4 后的映射：

```text
target_speed_cmps = normalized_command / 1000 × 60
```

例如：

| normalized | 目标轮速 |
|---:|---:|
| 100 | 6 cm/s |
| 200 | 12 cm/s |
| 220 | 13.2 cm/s |
| 280 | 16.8 cm/s |
| 300 | 18 cm/s |
| 1000 | 60 cm/s |

### 5.2 最终硬件输出

`Motor_SetSpeed()` 负责：

- 将命令限幅到 `-1000～1000`；
- 根据正负号设置 TB6612 方向 GPIO；
- 换向前先强制相应 PWM 为低；
- 将绝对值映射为 TIMG8 compare；
- 零命令时强制 PWM 低；
- 保存 requested、applied、compare 和方向诊断。

当前 PWM：

```text
TIMG8 / BUSCLK 32 MHz
timerCount = 1600
频率 = 32 MHz / 1600 = 20 kHz
MOTOR_A_PWM = PB15
MOTOR_B_PWM = PB16
```

`Motor_Stop()` 在临界区内同时强制两路 PWM 为低、清方向 GPIO 和运行时命令。软件 PWM 代码仍在，但只在 `FEATURE_HW_MOTOR_PWM=0` 时编译使用。

### 5.3 编码器解码与里程

当前硬件：

| 信号 | 引脚 | 行为 |
|---|---|---|
| MOTOR_A_ENCA | PA15 | 上升沿和下降沿中断 |
| MOTOR_A_ENCB | PA16 | ISR 内读取方向 |
| MOTOR_B_ENCA | PA17 | 上升沿和下降沿中断 |
| MOTOR_B_ENCB | PA24 | ISR 内读取方向 |

ISR 在 ENCA 每个边沿读取 ENCA/ENCB 相位关系，因此属于 ENCA 双边沿 ×2 解码。

当前标定：

```text
encoder_ppr_x2         = 734 pulse/rev
wheel_diameter_cm      = 6.5 cm
wheel_track_cm         = 11.25 cm
left_encoder_direction = -1
right_encoder_direction= +1
```

计算关系：

```text
distance_per_pulse = π × wheel_diameter_cm / encoder_ppr_x2
raw_speed_cmps = delta × distance_per_pulse × 1000 / elapsed_ms
wheel_distance = total_pulse × distance_per_pulse
center_distance = (left_distance + right_distance) / 2
```

轮速使用 `alpha=0.35` 的一阶 IIR：

```text
filtered = previous + 0.35 × (raw - previous)
```

估算器接受 `0 < elapsed ≤ 100 ms`，但 `elapsed > 60 ms` 会标为 stale；配置错误、计数溢出和非法 dt 都会进入 `error_flags`。累计脉冲和距离不会在每次动作开始时清零，定距动作只保存一个中心里程基准。

### 5.4 双轮轮速闭环

左右轮独立执行：

```text
error = ramped_target_speed - measured_filtered_speed
feedforward = ramped_target / 60 × 1000 × feedforward_gain
output = feedforward + kp_used × error + ki × integral
```

当前参数：

| 参数 | 左轮 | 右轮 |
|---|---:|---:|
| 最大映射速度 | 60 cm/s | 60 cm/s |
| 加速侧 Kp | 4.0 | 4.0 |
| 超速侧 Kp | 5.0 | 5.0 |
| Ki | 1.0 | 1.0 |
| 前馈系数 | 0.6 | 0.6 |
| 积分限幅 | 300 | 300 |
| 积分释放倍率 | 4 | 4 |
| 最大加速度 | 60 cm/s² | 60 cm/s² |
| 最大减速度 | 120 cm/s² | 120 cm/s² |
| 目标刷新超时 | 100 ms | 100 ms |

闭环还包含：

- 输出限幅和 anti-windup；
- 超速侧使用更高 Kp；
- 误差换向时快速释放积分；
- 目标斜坡与安全换向；
- 零目标直接停车；
- 估算器无效、stale、错误或反馈超范围时锁存停车；
- 非 `CAR_STATE_RUNNING` 时停车；
- 急停、watchdog 和 SafetyHold 抑制输出；
- 上层超过 100 ms 不刷新非零目标时故障停车。

发生控制错误后，普通 Stop 不会自动清除 `error_latched`；应通过 K3 长按执行完整复位。

## 6. P5 七路循迹

### 6.1 传感器和误差

七路数字量从左到右为 S1～S7，黑线有效，权重为：

```text
S1   S2   S3   S4   S5   S6   S7
-300 -200 -100   0  +100 +200 +300
```

多个传感器同时有效时取有效权重的平均值。

### 6.2 当前控制公式

```text
raw_error
→ error IIR，alpha=0.35
→ 使用真实 elapsed 计算微分
→ derivative IIR，alpha=0.20
→ correction = 0.60 × filtered_error
             + 0.010 × filtered_derivative
→ correction 限幅 ±260
→ left  = 300 + correction
→ right = 300 - correction
```

普通 FOLLOW 不允许反转。某侧命令落在 `1～49` 时会直接归零，避免低于稳定运行区间。

### 6.3 全白恢复

`LineController` 在仍看到线时记录边缘方向：

```text
S1 有效且 S7 无效 → 记为 LEFT
S7 有效且 S1 无效 → 记为 RIGHT
```

进入全白后：

```text
记为 LEFT  → left=0,   right=280
记为 RIGHT → left=280, right=0
重新看到任意黑线 → 当周期恢复 FOLLOW
持续全白 2000 ms → STOP / RECOVER_TIMEOUT
全白但此前没有方向 → STOP / NO_DIRECTION
```

P5 的丢线恢复位于 `LineController` 内，不依赖已关闭的旧 `TRACK_MODE_LOST_RECOVER`。

### 6.4 当前调参边界

真正控制 P5 的参数是 `line_control_v2_*` 字段。OLED 参数页在
`FEATURE_LINE_CONTROL_V2=1` 时已经直接绑定当前 V2：

```text
SPD  line_control_v2_base_command，步长10，范围100～500
FF   左右轮共同 feedforward_gain ×100，步长5，范围50～80
KP   line_control_v2_kp ×100，步长5，范围0～200
KD   line_control_v2_kd ×1000，步长1，范围0～100
MAX  line_control_v2_max_correction，步长10，范围0～SPD
```

`SPD<=500` 且 `MAX<=SPD` 保证 `SPD+MAX<=1000`，最大修正只会把内侧轮降到 0，
不会让普通 FOLLOW 反转。FF 同时修改左右轮前馈但不改变目标轮速，适合重载时增加维持
同一速度所需的基础输出。修改 V2 参数后会清循迹 PD 历史；修改 FF 后会复位轮速控制器，
且参数页只允许从 READY 状态进入。所有按键修改仍只保存在 RAM，断电后恢复编译默认值。

### 6.5 循迹有效行驶时间

`AppRuntime.line_follow_elapsed_ms` 记录本次 FOLLOW_LINE 的有效控制时间。每次
`CarController_StartFollowLine()` 真正启动时清零，只有 `handle_follow_line()` 获得控制权时
才按调度器传入的真实 `elapsed_ms` 饱和累加。因此暂停、SafetyHold、等待、转角、定距和停车
均不计时；V2 丢线寻找仍在驱动车轮，所以继续计时。STOP和动作结束后保留最终值，下一次
FOLLOW_LINE 开始时再清零。

任务暂停会冻结当前值，恢复当前动作时走不清零的恢复入口并继续累计；避障或 SafetyHold
解除后重新把控制权交还给同一段 FOLLOW_LINE 时也不会重置计时。只有新的 FOLLOW_LINE 动作
首次启动或整车运行时复位，才会从 `00:00.0` 重新开始。

计时值进入 `RuntimeSnapshot`，OLED LINE 页每 100 ms 显示一次：

```text
T:MM:SS.t
```

其中 `t` 为十分之一秒。计时不依赖OLED刷新次数，切换页面也不会影响累计结果。

## 7. IMU、航向、转角和定距

### 7.1 IMU 与 HeadingControl

当前 MPU6050 关键参数：

```text
gyro 量程        ±500 °/s
灵敏度           65.5 LSB/(°/s)
Yaw 轴符号       -1
gyro 死区        1.5 °/s
有效 dt          5～100 ms
短缺帧补偿上限   60 ms
stale 阈值       100 ms
Yaw 范围         [-180°, 180°)
```

上电初始化先对 MPU6050 写 `PWR_MGMT_1=0x80` 执行器件复位，等待后再写
`PWR_MGMT_1=0x01` 使用 X 轴陀螺仪 PLL。零偏标定仍采集 200 点，但增加启动验收：

```text
平均零偏绝对值       <= 10 °/s
标定样本峰峰值       <= 5 °/s
标定后20点修正角速度 <= 3 °/s
失败自动重试         最多3次
```

三次均失败时 `calibrated=false`、`valid=false`，Yaw 不积分，依赖 IMU 的动作不会启动；
不再通过反复人工 RST 碰运气获取一次正常零偏。

`HeadingControl` 使用绝对 Yaw 目标：

```text
error = Normalize180(target_yaw - current_yaw)
derivative = -gyro_z_dps
correction = clamp((30 × error + 5 × derivative) / 10, -30, 30)
```

注意：当前源码 `heading_kp=30`，已不同于 2026-07-24 P6 方案中记录的 20。

### 7.2 当前允许的动作

新底层正式允许：

```text
FOLLOW_LINE
TURN_TO_YAW
DRIVE_HEADING_UNTIL_LINE
DRIVE_DISTANCE
DRIVE_DISTANCE_HEADING
WAIT
STOP
```

以下旧动作类型仍留在枚举或源码中，但在 `FEATURE_LEGACY_MOTION_CONTROL=0` 时不会成为合法任务动作或获得控制权：


### 7.3 相对 Yaw 转角

启动时：

```text
target_yaw = Normalize180(current_yaw + relative_angle)
```

运行逻辑：

```text
|error| > 12°      → 双轮反向，命令 220
5° < |error| ≤ 12° → 双轮反向，命令 160
|error| ≤ 5°       → 0/0，检查 |gyro| ≤ 5 °/s
连续稳定 100 ms    → SUCCESS
达到 timeout       → ERROR 并持续停车
```

2026-07-27 左右方向实车测试发现旧命令 130/65 下右轮无法稳定克服静摩擦，因此当时只提高
TURN 层的快速/慢速命令到 220/160。后续重载循迹测试又把 P4 左右轮前馈默认值统一提高到
0.60，并把 P5 默认值固化为 SPD=300、KP=0.60、KD=0.010、MAX=260。

当前没有独立 FAST/SLOW/SETTLE 枚举，也没有 7°退出迟滞；这是 P6 文档的建议状态机，不是当前源码事实。

蓝牙动作层只允许 `±45°`、`±90°` 和 `180°`，不开放 5°微转。`TURN,180`
和 `TURN,-180` 都按同一个顺时针方向执行。当前工程沿用“相对角度 +90°为顺时针”
的车辆约定，并通过 `yaw_turn_direction_hint` 解决恰好 180°时 `[-180,180)`
归一化产生的方向二义性；烧录后仍须用架空轮测试确认一次物理方向。

蓝牙 TURN 的动作超时取 `max(yaw_turn_timeout_ms, 4000 ms + |angle| × 40 ms)`，
所以 45°、90°、180°当前分别约为 5.8 s、7.6 s、11.2 s。该裕量包含接近目标后的
低速段和 100 ms 稳定判定，但超时后仍会进入 ERROR 锁存，不会自动继续接受下一条动作。

### 7.4 绝对航向找线

`DRIVE_HEADING_UNTIL_LINE(target_yaw, command, timeout)` 用于从无黑线区域沿绝对 Yaw 前进，任意一个循迹传感器看到黑线后动作成功。

当前 RACE-1 使用：

```text
target_yaw = 0°
command = 200
timeout = 5000 ms
```

该 0° 是上电 IMU 校准并清零后的绝对 Yaw，不是进入动作时自动锁存的当前方向。

### 7.5 定距

当前有两个底层动作：

```text
DRIVE_DISTANCE(distance_cm, command)
DRIVE_DISTANCE_HEADING(distance_cm, absolute_target_yaw, command)
```

`distance_cm` 现在是有符号距离：正数前进，负数后退；`command` 仍是正的速度
幅值，由动作启动函数转换成对应方向的左右轮目标。共同逻辑：

```text
direction = sign(distance_cm)
target_distance = abs(distance_cm)
start = center_distance_cm
travelled = direction × (current_center_distance - start)
remaining = target_distance - travelled

LOW：remaining > 5.0 cm → 保持 25 cm/s
HIGH：先保持 45 cm/s
HIGH 到达总路程 80% 后 → 降到 25 cm/s
HIGH 的减速区至少为 20 cm；目标距离 ≤ 20 cm 时从起步即按 25 cm/s
0.8 cm < remaining ≤ 5.0 cm → 最终命令不高于 130（约 7.8 cm/s）
remaining ≤ 0.8 cm → 0/0，进入 SETTLE
左右轮速都 ≤ 2.0 cm/s，持续 200 ms → DONE
```

高速动态减速区为 `max(目标距离 × 20%, 20 cm)`，但不会大于目标距离本身。因此
`MOVE,100,HIGH` 在约 80 cm 处降到 25 cm/s，`MOVE,200,HIGH` 在约 160 cm 处降速。
低速 MOVE 仍沿用已实车验证的固定 5 cm 精调区，不改变其现有精度。

`DRIVE_DISTANCE_HEADING` 还会：

- 支持指定绝对 Yaw，也支持 `lock_current_yaw_on_start`；
- 蓝牙 MOVE 使用后者，只有动作真正获得控制权且 IMU Ready 时才读取并锁存当前 Yaw，不在刚收到蓝牙字符时读取；
- 要求动作开始时与目标 Yaw 的差不超过 20°；
- 使用 HeadingControl 修正左右命令；
- 按速度幅值动态限幅 correction，使前进时两轮保持非负、后退时两轮保持非正，并且绝对值不超过 1000。

当前实现边界：

- 前进与后退共用同一个定距状态机、减速区和停稳判定；后退航向修正符号尚需实车扰动验收；
- 没有越界后反向修正；越过终点会直接进入停车/停稳判断；
- P6.3 已有源码与 OLED 诊断，但未找到 20/50/100 cm、不同速度、扰动、异常等完整实车验收记录；
- Pause 会 `MotionAction_Init()`，Resume 后会从当前位置重新开始当前动作的完整目标距离，不会继续剩余距离；定距任务调试期间不要使用 Pause/Resume。

## 9. 安全、障碍与故障

### 9.1 软件急停和复位

- 任意普通页面 K2 长按：触发软件急停，立即停车。
- 急停状态下 K3 长按：解除急停并回 HOME。
- 普通状态 K3 长按：清 Fault、重置 watchdog、任务、CarController、MotorControl 和避障状态，保持停车等待重新启动。

### 9.2 Watchdog

当前只有软件 heartbeat watchdog。它可在 SysTick 仍运行、主控制长期没有完成时从 ISR 路径强制 `Motor_Stop()`。

`FEATURE_HARDWARE_WATCHDOG=0`，`empty.syscfg` 没有已审核的硬件 WWDT 实例，因此不能把当前工程描述为具有硬件 watchdog 复位覆盖。

### 9.3 超声波和 STOP_ONLY

HC-SR04 当前阈值：

```text
距离 < 20 cm，连续 3 次 → BLOCKED
距离 ≥ 25 cm，连续 3 次 → CLEAR
20～25 cm → 保持原状态
```

当前新底层所有可见 FOLLOW 任务使用 `OBSTACLE_POLICY_STOP_ONLY`：

```text
BLOCKED
→ CarController SafetyHold
→ MissionManager ExternalHold
→ 电机停车，任务时间冻结
→ 障碍清除后解除 Hold，继续当前动作
```

### 9.4 固定主动绕障的当前状态

旧固定绕障状态机源码仍在 `obstacle_avoidance.c`，但主体被 `FEATURE_LEGACY_MOTION_CONTROL` 包围。当前开关为 0，因此：

- 固定主动绕障运行逻辑不执行；
- MissionLibrary 会拒绝新底层任务中的 `OBSTACLE_POLICY_FIXED_BYPASS`；
- 当前真正生效的只有 STOP_ONLY 安全停车；
- 舵机扫描器也处于关闭状态。

旧《工程文档》中“+35° → 航向直行 1400 ms → -55° → 回线”的描述只属于保留的旧链路，不是当前新底层主线。

## 10. HC-06 蓝牙联调（历史实现，当前停用）

> 2026-07-30资源调整：`FEATURE_BLUETOOTH_UART=0`，`empty.syscfg`已移除
> `UART_BLUETOOTH`，PB6/PB7不再配置为UART，现已改作平衡轴AB编码器输入。以下内容仅保留为历史调试和协议参考，
> 当前比赛方案使用PB2/PB3的`UART_VISION`与K230或树莓派进行有线通信。

### 10.1 当前已经实现

```text
HC-06 Bluetooth Classic SPP
↕ 9600 8N1，无流控
MSPM0 UART1
↕ RX 中断 + 主循环轮询兜底 / TX FIFO 中断发送
bluetooth_uart.c
↕
128 字节 RX 环形缓冲 + 256 字节 TX 队列 + Runtime 诊断
↕
App 层行协议 / MissionManager 临时动作 / OLED BT 页面
```

硬件连接按 MCU 方向命名：

| MCU | HC-06 | 说明 |
|---|---|---|
| PB6 UART TX | 模块 RXD | MCU 发、模块收 |
| PB7 UART RX | 模块 TXD | 模块发、MCU 收 |
| GND | GND | 必须共地 |

配置：

```text
UART_BLUETOOTH = UART1
baud = 9600
data = 8 bit
parity = none
stop = 1 bit
flow control = none
RX interrupt = enabled
FIFO = enabled
```

固件按 HC-06 常见出厂透明串口参数 9600 8N1 工作，不会在小车启动时自动
进入 AT 模式或反复修改模块配置。HC-06 的 AT 行为在不同克隆固件间有差异，
且通常只在未建立蓝牙连接时有效；若新模块曾被改过波特率，应先用 USB-TTL
在断开蓝牙连接的状态下恢复/确认 9600，再接入小车。

`BluetoothUart_Init()` 会清空 RX head/tail、清计数并使能 UART1 IRQ。RX ISR 会：

- 读取所有可用字节；
- 更新 `irq_count`、`rx_byte_count` 和 `last_rx_byte`；
- 将字节写入 128 大小的环形缓冲；
- 在仅用于物理联调的 `FEATURE_BLUETOOTH_RX_ECHO=1` 时立即把字节回显给电脑；正式协议当前设为 0；
- 缓冲满时保留旧数据、丢弃新字节并增加 `rx_overflow_count`。

主循环持续调用 `BluetoothUart_Process()`：它读取 PB6/PB7 的 PINCM 复用状态
和 PB7 当前电平；若 UART 硬件中已经有数据但 RX 中断未处理，则以轮询方式取出并增加
`polled_rx_byte_count`。正常情况下字节应走中断，`P` 保持 0；若 `RX`
增长且 `P` 同步增长，则说明字节是由轮询兜底救回，应该继续排查 NVIC/IRQ。

RX 环形缓冲用一个空槽区分满/空，实际最多保存 127 个尚未消费的字节。
应用回复先完整进入 256 字节 TX 环形队列，再送入 UART FIFO。只要软件 TX 队列中仍有数据，
就动态开启 TX 中断继续补充 FIFO；队列清空后关闭 TX 中断。`BluetoothUart_Process()` 仍保留
主循环发送兜底。这一修改用于降低主循环瞬时忙碌时回复缺字节的概率。

App 行解析器只接受 TAB 和 ASCII 0x20～0x7E。行首 NUL、蓝牙刚连接时的非打印垃圾字节会被
直接忽略；合法命令中间出现非法字节则丢弃整帧并返回 `ERR,FORMAT`。尚未收到换行的残帧若
连续 100 ms 没有新字节会被静默清空，避免关闭并重开 SPP 后把旧半帧与新命令拼接。

### 10.2 当前动作协议

每条命令以 LF 或 CRLF 结束，最长 63 字节；命令不区分大小写。第一版支持：

```text
PING
HB
STATUS
MOTOR
SPEED,LOW
SPEED,HIGH
MOVE,<有符号距离cm>
MOVE,<有符号距离cm>,LOW|HIGH
MOVE,<有符号距离cm>,25|45
TURN,45
TURN,-45
TURN,90
TURN,-90
TURN,180
STOP
ESTOP
RESET
MAGNET,ON
MAGNET,OFF

CMD,<序号>,MOVE,<有符号距离cm>,LOW|HIGH
CMD,<序号>,TURN,<角度>
CMD,<序号>,MAGNET,ON|OFF
```

速度档只有两挡：`LOW=25 cm/s`、`HIGH=45 cm/s`。例如：

```text
MOVE,50,LOW    前进 50 cm，25 cm/s，并在真正启动时锁存当前 Yaw
MOVE,-50,HIGH  后退 50 cm，45 cm/s，并保持启动航向
```

App 层按 `wheel_control_max_speed_cmps` 把物理速度换算为 normalized command；树莓派
不接触 PWM 或 P4 参数。动作由 `MissionManager_StartTransientAction()` 复制到内部静态
临时任务中执行，因此不会与普通任务同时拥有 CarController。Pi 侧第一版应一次只发送
一个 MOVE/TURN，MCU 忙时返回 `BUSY`；STOP 和 ESTOP 可以抢占。

典型应答：

```text
PONG
STATUS,<车辆状态>,<运行模式>,<故障码>,<速度挡>,H=<安全保持>,OBS=<超声波cm或NA>,MAG=ON|OFF,A=<当前动作>,AE=<动作已运行ms>,AI=<当前动作ID>,LID=<最近动作ID>,LA=<最近动作>,LR=<最近结果>,LMS=<最近耗时>,LE=<最近错误码>,RO=<RX溢出>,TD=<TX丢弃>,CS=<最近CMD序号>,CC=<最近CMD名称>,CR=<RUN|ACK|DONE|ERR|CANCEL>,RL=<远程失联锁存>,LT=<累计失联次数>
MOTOR,C=<左右normalized>,T=<左右目标cm/s>,M=<左右实测cm/s>,O=<左右PWM>,E=<闭环错误位>
ACK,MOVE,LOW,ID=<动作ID>,T=<3507动作超时ms>
DONE,MOVE,ID=<动作ID>,MS=<实际动作耗时ms>
ACK,TURN,ID=<动作ID>,T=<3507动作超时ms>
DONE,TURN,ID=<动作ID>,MS=<实际动作耗时ms>
ACK,STOP
ACK,ESTOP
ACK,RESET
ACK,MAGNET,ON
ACK,MAGNET,OFF
ERR,MAGNET,PARAM|SAFETY|BUSY|HARDWARE
ERR,MOVE,<错误码>,ID=<动作ID>,MS=<实际动作耗时ms>
ERR,TURN,<错误码>,ID=<动作ID>,MS=<实际动作耗时ms>
ERR,TURN,3,E=<剩余角差>,Y=<当前Yaw>,G=<当前Z轴角速度>,ID=<动作ID>,MS=<动作耗时>
ERR,RESET_REQUIRED

ACK,17,MOVE,LOW,ID=<内部动作ID>,T=<3507动作超时ms>
DONE,17,MOVE,ID=<内部动作ID>,MS=<实际动作耗时ms>
ERR,17,MOVE,<错误码>,ID=<内部动作ID>,MS=<实际动作耗时ms>
ACK,19,MAGNET,ON
ERR,19,MAGNET,<原因>
```

这里有两种编号：`ID` 是 3507 为每次真正启动的 MOVE/TURN 分配的内部诊断号；`CMD` 序号由
电脑、树莓派或 K230 在发送前分配，用于防止链路重试造成重复运动。手动命令保持原格式，正式
自动控制使用 `CMD,<序号>,...`。3507 在 RAM 中缓存最近一条 CMD 的规范化内容、ACK 和最终
DONE/ERR/CANCEL 结果，RESET 不清除缓存，重新上电会清除。

CMD 重发规则：

```text
同序号 + 同内容 + RUN       → 只重发原 ACK，不重新启动动作
同序号 + 同内容 + 已结束    → 只重发缓存的 DONE/ERR/ACK
同序号 + 不同内容           → ERR,<序号>,<命令>,SEQ_CONFLICT
旧 CMD 仍为 RUN 时发新序号  → ERR,<新序号>,<命令>,BUSY
不支持的 CMD 内层命令       → ERR,<序号>,<命令>,UNSUPPORTED
```

第一版只允许 CMD 包装 MOVE、TURN 和 MAGNET，并要求上位机一次只保留一条在途命令。STOP、
ESTOP 和不带 CMD 的 `MAGNET,OFF` 始终保留为无条件安全通道。若3507重新上电导致 `CS=0`，
上位机必须视为新会话并停止旧任务，不能猜测断电前动作是否完成。

正式自动控制的 `CMD MOVE/TURN` 带通信看门狗。动作真正启动后，上位机每 400 ms 发送一次
单向 `HB\n`；3507 收到 `HB` 不回复，收到 `PING` 或合法 CMD 也会刷新最后联系时间。若连续
1500 ms 没有联系，3507 会立即停止电机、取消临时动作，并缓存：

```text
ERR,<CMD序号>,MOVE|TURN,LINK_TIMEOUT,ID=<内部动作ID>,MS=<已运行时间>
```

同时 `RL=1`、`LT` 加一。失联不会自动关闭电磁铁，以免搬运途中立刻掉落物资；但会拒绝新的
远程 MOVE/TURN 和 `MAGNET,ON`，直到收到 `RESET`。`RESET` 会清除 `RL`，同时按既有安全
规则关闭电磁铁，且绝不自动续跑断联前的动作。普通无 CMD 的手动 MOVE/TURN 和本地任务不受
该通信看门狗保护，因此比赛自动控制必须使用 CMD 格式。

`STOP` 停止并取消普通动作，但不清故障，也不改变当前电磁铁状态，便于小车停车后继续
保持物资。`ESTOP` 进入锁存急停并持续强制电机与电磁铁关闭；`RESET` 首先关闭电磁铁，
再统一清理急停、watchdog、控制器错误、任务临时状态和故障后回到 READY，且不自动恢复
先前动作。

`MAGNET,OFF` 在任意状态都允许执行。`MAGNET,ON` 仅在无故障、无急停、watchdog 未触发，
且车辆和任务均未处于 RUNNING/PAUSED 时允许；拒绝原因分别返回 `SAFETY` 或 `BUSY`。
磁铁已经开启后允许再启动 MOVE/TURN，以便搬运物资。任意 `Fault_Raise()`、任务/车辆 ERROR、
急停和 watchdog 超时都会绕过普通协议逻辑，直接拉低 PB5。上电和复位同样默认关闭。
其中 TURN 错误码 `3` 是转向超时。收到它后必须先发 `RESET`；扩展字段保留 0.1°/0.1°/s
分辨率，可用于判断是剩余角差过大，还是角度已经到位但角速度稳定条件未通过。

当前仍未实现的是 Flash 参数保存。超声波小于 20 cm 的现有 SafetyHold 仍会作用于
MOVE/TURN；以后进入拾取阶段时，应把“识别到物资 → 停车 → 开启电磁铁”设计成上层任务，
不在本轮改变定距减速与停稳策略。

### 10.3 OLED 蓝牙页

紧凑页面循环中有 BT 页，显示：

```text
I    初始化标志
M    PB6/PB7 当前 PINCM 是否仍为 UART1 TX/RX；1 表示未被云台 GPIO 覆盖
H    PB7 当前电平；UART 空闲时通常为 1
RX   ISR 或轮询已收到的累计字节数
L    最后收到字节的十进制值
IRQ  UART1 中断处理函数进入次数
P    被主循环轮询兜底取出的字节数
T    已送入 UART 硬件的累计 TX 字节数
O    RX 环形缓冲溢出次数
D    TX 回复队列满时丢弃的累计字节数
```

发送 `PING` 加换行时，正确现象应为：

```text
RX 增加 5
L 显示 10（LF）
M 保持 1，H 空闲时为 1
IRQ 增加，P 保持 0
T 随 `PONG\r\n` 增加，O/D 保持 0
```

PC 工具应收到 `PONG`，不再收到逐字节原样回显。若 `RX` 增加但没有协议回复，查看
最后字节是否为 LF、`T` 和 `D`；若 `RX` 不变但 `P` 增加，说明接收中断存在问题。

### 10.4 PC 调试工具

工具：

```text
tools/bluetooth_serial_console.py
```

依赖：

```powershell
pip install pyserial
```

常用命令：

```powershell
python tools/bluetooth_serial_console.py --list
python tools/bluetooth_serial_console.py --scan
python tools/bluetooth_serial_console.py --port COMx
python tools/bluetooth_serial_console.py --port COMx --command "PING"
python tools/bluetooth_serial_console.py --port COMx --hex "41"
```

`--scan` 会扫描 Windows 中已经配对并创建了 SPP“传出”COM 口的设备，显示
设备名、COM 号和蓝牙地址，然后等待输入序号并直接连接。例如当前电脑会显示：

```text
[1] COM8  HC-04       04:25:02:08:02:1C
[5] COM15 JDY-31-SPP  CC:DF:24:46:5A:2D
```

未完成 Windows 配对、没有 SPP Serial Port 服务或只有“传入”端口的设备不会
出现在可选列表中。连接前必须完全退出 HC-PC、串口助手和其他占用该 COM 的
程序；“拒绝访问”表示端口仍被占用，“信号灯超时”表示 Windows 未能建立
SPP 链路。

更换模块后必须先在 Windows 删除/忽略旧模块的 COM15，重新配对 HC-06，
再用 `--list` 确认新生成的出站 COM 口。工具不再内置旧模块蓝牙地址；若
Windows 串口描述中没有显示 `HC-06`，必须显式传入 `--port COMx`，也可以
用 `--address` 传入新模块蓝牙地址辅助自动识别。

进入交互模式、执行 `--command` 或 `--plan` 前，工具会等待 SPP 稳定约 500 ms，清空电脑端
旧输入，发送一个空 LF 终止底盘残帧，再执行最多 3 次 PING/PONG 同步。只有同步成功后才允许
发送用户命令或动作计划。`--send` 与 `--hex` 是原始字节调试模式，不自动插入同步帧。

交互模式内：

```text
test              发送 PING + LF，期待 PONG
cmd <command>     发送一条协议命令并附加 LF
check <plan.txt>  只检查连续动作计划，不执行
run <plan.txt>    顺序执行动作计划，遇到超时或ERR立即中止
send <text>       原样发送文本
line <text>       文本后附加 LF
hex AA 55 01      发送十六进制字节
ports             列出串口
quit              退出
```

工具刻意不把普通键盘输入直接变成运动命令；运动命令必须显式使用 `cmd`。
`--command` 会等待约 1 秒读取立即应答，适合 PING/STATUS 等一次性测试；MOVE/TURN
应在交互模式使用 `cmd CMD,<序号>,...`，持续观察后续 DONE/ERR，并保留随时发送
STOP/ESTOP 的通道。交互控制台打开期间会在后台每 400 ms 发一次无回包 `HB`，避免手动
测试 CMD 动作时误触发底盘通信看门狗；退出程序或串口断开后心跳自然停止。

连续动作计划每一行都必须显式给出上位机超时：

```text
<timeout_seconds> <command>
```

例如 `tools/bluetooth_action_plan_example.txt`：

```text
2 RESET
2 SPEED,LOW
6 MOVE,30,LOW
8 TURN,45
6 MOVE,-30,LOW
2 MAGNET,ON
1 WAIT,500
2 MAGNET,OFF
```

其中 `WAIT,<ms>` 是PC端本地等待，不会发送给3507。计划可以先静态检查，再连接COM9执行：

```powershell
python tools/bluetooth_serial_console.py --check-plan tools/bluetooth_action_plan_example.txt
python tools/bluetooth_serial_console.py --port COM9 --plan tools/bluetooth_action_plan_example.txt
```

计划文件仍写普通 MOVE/TURN/MAGNET，不需要手填序号。执行前工具先查询 STATUS，从 `CS+1`
开始编号，并在发送时自动转换，例如 `MOVE,30,LOW` 实际发送为 `CMD,17,MOVE,30,LOW`。
MOVE/TURN收到 ACK 后进入 DONE 等待，收到同一 CMD 序号的 DONE 后才发送下一行。每步上位机
超时独立计算，并应大于 ACK 中3507返回的 `T=<ms>`；若配置不大于底层超时，工具会报警。
等待 MOVE/TURN 的 ACK 和 DONE 期间，工具每 400 ms 发送 `HB`。开始新计划前若 STATUS 显示
`CR=RUN`，工具先 STOP；若显示 `RL=1`，工具先 RESET，再从最新 `CS+1` 编号。

ACK 未收到时，工具最多发送同一条 CMD 三次；因为序号和内容不变，3507只会重发缓存应答，
不会再次移动。MOVE/TURN达到上位机总超时后，工具先发送STOP，再重发一次原 CMD读取缓存：
缓存为 DONE 才恢复成功并继续，缓存为 CANCEL/ERR或无法核验则中止。MAGNET超时后始终发送
无序号的 `MAGNET,OFF` 并中止，不会因为丢回复而让磁铁保持未知状态。

固定错误处理策略如下；无论采取哪种恢复动作，当前计划都中止，不跳过失败动作，也不会在
RESET 后自动恢复剩余队列：

| 情况 | PC 工具处理 |
|---|---|
| `BUSY` / `SEQ_CONFLICT` / `UNSUPPORTED` / 参数错误 | 查询 STATUS 后中止，不 RESET |
| MOVE/TURN 动作错误或 CANCELLED | STOP → STATUS → 中止 |
| 数字动作错误、`RESET_REQUIRED`、`LINK_TIMEOUT`、`LINK_LOST` | STOP → STATUS → RESET → STATUS → 中止 |
| `MAGNET,HARDWARE` | `MAGNET,OFF` → STATUS → 中止 |
| MAGNET 上位机超时 | `MAGNET,OFF` → 中止 |
| 串口/SPP 断开 | 不再发后续动作；依靠3507在 1.5 s 内停车，重连后重新决策 |

所谓“重试”只允许原序号、原内容完全相同的协议重发，绝不生成新序号重复执行距离。运行计划
时按 Ctrl+C 也会先尝试发送 STOP。

日志中的 `[RX 1 B] 'D'` 随后接 `[RX 18 B] 'ONE,...'`、或 ACK 被拆成两段，属于操作系统和
SPP 的正常串口分包，行接收器会重新拼成完整 CR/LF 行；只有最终缺少完整协议行、出现
`RX ERROR`、串口异常或动作超时，才按链路异常处理。

### 10.5 树莓派阻塞式控制接口

比赛上位机使用：

```text
tools/chassis_bluetooth.py
```

它是一次只执行一个动作的阻塞接口，Windows COM 口和树莓派 `/dev/rfcomm0` 都可使用。
连接时会完成残帧清理、PING/PONG 同步和 STATUS 序号同步；MOVE/TURN/MAGNET 自动包装为
CMD，MOVE/TURN 等待期间自动发送心跳。ACK 丢失时只重发同序号命令，DONE 丢失时通过
STOP 和同序号缓存查询确认结果。任何 ERR、超时或链路异常都抛出异常，不会静默发送下一步。

树莓派安装与 RFCOMM 建链示例：

```bash
sudo apt install bluez python3-serial
bluetoothctl
# 在 bluetoothctl 内执行：scan on、pair <HC06_MAC>、trust <HC06_MAC>、connect <HC06_MAC>、quit
sudo rfcomm bind 0 <HC06_MAC> 1
python3 tools/chassis_bluetooth.py --port /dev/rfcomm0 --verbose
```

最后一条命令只连接、同步并打印 STATUS，不会让小车运动。业务代码示例：

```python
from tools.chassis_bluetooth import ChassisBluetooth, ChassisError

try:
    with ChassisBluetooth("/dev/rfcomm0") as car:
        print(car.status())
        car.move(30, "LOW")
        car.turn(45)
        car.magnet(True)
        car.move(-30, "LOW")
        car.magnet(False)
except ChassisError as exc:
    print(f"底盘任务中止：{exc}")
    # 不在这里盲目继续后续动作，由比赛状态机重新观察并决策。
```

`move()`、`turn()` 返回 `CommandResult`，其中包含 CMD 序号、ACK、最终 DONE 和耗时。接口的
主要异常为 `ChassisLinkError`、`ChassisProtocolError`、`ChassisCommandError` 和
`ChassisTimeoutError`。重连时若发现旧 `CR=RUN` 会先 STOP；若发现 `RL=1` 会 RESET，注意
RESET 会关闭电磁铁，因此上层必须把这次重连当作新任务起点，不能假定物资仍在原状态。

此 Python 类面向 CPython + pyserial，可直接运行在树莓派。K230 或树莓派以后改成板间有线 UART
时仍沿用相同 CMD/HB/ACK/DONE/ERR 状态机，但应为对应运行环境实现串口适配层，不把蓝牙
配对和 RFCOMM 建链代码塞进底盘协议。

### 10.6 蓝牙、电磁铁与云台的资源冲突（历史状态）

PB5仍用于电磁铁继电器；HC-06已停用，PB6/PB7已转作平衡轴编码器。当前配置为：

```c
FEATURE_BLUETOOTH_UART = 0
FEATURE_MAGNET_RELAY = 1
FEATURE_GIMBAL_MOTION_CONTROL = 0
```

旧双轴云台仍然不能直接恢复：其PITCH轴历史定义占用PB5/PB6/PB7，其中PB5已经用于
电磁铁，PB6/PB7已经用于新平衡轴编码器。新平衡装置应建立独立单轴功能与引脚组，
不能直接打开`FEATURE_GIMBAL_MOTION_CONTROL`。

### 10.7 继电器与 5 V 电磁铁接线

本方案使用 3.3 V 高电平触发继电器模块，电磁铁额定 5 V、0.3 A。PB5 只输出控制信号，
不能直接给电磁铁供电。继电器使用 NO 常开触点，使控制器掉电、复位或 PB5 为低时磁铁释放。

```text
PB5                  → Relay IN
MCU GND              → Relay GND
Relay VCC            → 按继电器模块标称接 3.3 V 或 5 V

5 V 磁铁电源正极     → 保险丝 → Relay COM
Relay NO             → 电磁铁正极
电磁铁负极           → 5 V 磁铁电源负极
```

注意“3.3 V 输入”通常只说明 IN 可由 3.3 V GPIO 触发，不一定说明继电器模块 VCC/线圈也应接
3.3 V，必须按模块丝印或规格书供电。输入侧若不是完全光耦隔离，MCU 与继电器模块必须共地。
磁铁建议使用独立、稳压的 5 V 电源，持续电流能力至少留有余量（建议不低于 1 A），不要默认
由 MCU 板载小电流 5 V/3.3 V 稳压器承担。

电磁铁两端必须反向并联续流二极管：阴极接电磁铁正极，阳极接电磁铁负极；0.3 A 负载可用
1N4007。普通二极管会让释放稍慢，若后续实测需要快速释放，再将钳位方案改为合适的 TVS。
PB5 建议外接 10 kΩ 下拉，防止 MCU 上电高阻阶段误吸合；`empty.syscfg` 中 PB5 初始值也已设
为 `CLEARED`。继电器触点需要满足直流 5 V、0.3 A，并建议在磁铁供电支路加 0.5～1 A 保险。

## 11. OLED 与按键

### 11.1 当前紧凑页面循环

`FEATURE_OLED_LEGACY_DIAG_PAGES=0` 且蓝牙开启时：

```text
STATUS → SENSOR → HEADING → DISTANCE → BLUETOOTH → STATUS
```

源码注释也将其简称为：

```text
HOME → LINE → TURN → DIST → BT
```

旧 IMU 明细、编码器、MotorControl 和障碍页面代码仍保留；将 legacy diag 开关改为 1 后才进入更长的诊断循环。

OLED 每 100 ms 重建缓冲，并分行刷新显示，避免一次刷新占用过长。

LINE 页当前布局：

```text
LINE P:0011100
S:FOL E:-100/-82
C:-120 L:180 R:420
T:00:12.3 M:L R:-
```

最后一行的 `T` 是本次循迹有效行驶时间，`M` 是最近转向方向记录，`R` 是停止/恢复失败原因。

### 11.2 普通页面按键

```text
K1 短按  切换页面
K1 长按  进入参数页
K2 短按  READY→启动，RUNNING→暂停，PAUSED→恢复
K2 长按  软件急停
K3 短按  取消任务并回 READY
K3 长按  清故障并完整复位底层和任务
```

参数页：

```text
K1 短按  下一参数
K1 长按  返回进入参数页前的页面
K2 短按  增加
K2 长按  软件急停（全局安全键）
K3 短按  减少
K3 长按  减少；SV 项使用快速步长
```

当前参数项：

```text
TASK / SPD / FF / KP / KD / MAX / SV / WLK
```

其中 V2 下 `SPD/MAX` 直接显示 normalized command；`FF/KP/KD` 为适合整数 OLED 和按键的
缩放值，页面底行分别显示 `X0.01` 或 `X0.001`。SPD 页面同时显示对应物理速度的 10 倍值
`CM10`。WLK 在云台运动关闭时固定返回 0。

`P6收尾与新版底层全面迁移总体方案.md` 审计的是 2026-07-24 状态。此后源码已经发生以下关键变化：

2026-07-30开始平衡装置电机层第一阶段。当前不重新启用旧双轴云台，而是通过：

```c
FEATURE_BALANCE_STEPPER_OPEN_LOOP_TEST = 1
FEATURE_GIMBAL_MOTION_CONTROL = 0
```

直接复用`gimbal_stepper.c/.h`中已经实机使用过的单轴开环脉冲代码。当前固定测试参数：

```text
STEP：PB4
DIR ：PA1
EN  ：PA2
单次相对运动：200 STEP
STEP半周期：25 × 100 us
完整STEP频率：200 Hz
按3200 STEP/rev换算约3.75 RPM
```

上电只初始化并释放驱动器，不会自动运动。K1短按循环到平衡轴诊断页面后，按键语义由限位状态决定：

```text
Z:WAIT时K1长按：确认物理零点；有Flash则恢复限位，无Flash则进入首次完整标定
CAL时K2/K3短按：相对正/负微调20 STEP；停止后K1长按记录当前标定点
READY时K2/K3短按：按200 STEP理论位移生成正/负编码器目标，使用位置闭环运动
READY时K1长按：启动1秒周期、上下限各60%的连续平滑往复测试
位置闭环或连续往复中K1长按：立即取消并保持
READY时K3长按：释放EN并准备重新完整标定
位置故障锁存后K3长按：只清故障并保持，不自动重试动作
K2长按：全局急停，停止STEP并保持EN
急停后K3长按：复位并释放EN
```

平衡轴OLED关键字段：

```text
F：Flash状态，OK/NA/BAD/ERR
Z:WAIT：等待人工对准并确认物理零点
POS/P：相对本次确认零点的编码器逻辑位置
ENC：AB×4后的编码器原始累计计数
S：累计发送的STEP开环估算位置
L/H：软件数值下限/上限
TEST:LOW/HIGH/ZERO：自动安全行程测试阶段
POSCTRL:RUN/SET：位置闭环运动/稳定判定
P/T/E/FE/R：当前位置、目标、位置误差、STEP换算跟随误差、STEP频率
POS FAULT：位置故障锁存；NOENC/FOLLOW/DIR/TIME/LIMIT表示具体原因
```

本阶段验收只要求：

```text
正向200 STEP能够自动停止
反向200 STEP能够自动停止
正反连续切换时方向正确且STEP先回到低电平
自动测试中K1长按能停止并保持
READY状态K3长按能释放驱动器并进入重新标定准备
K2长按急停后不再输出STEP
在计划负载下连续往返10次无明显卡顿或失步
```

编码器采集实现位于独立的`balance_encoder.c/.h`，不会调用或清除底盘`encoder.c`的左右轮
累计数据。PB6/PB7均配置为内部上拉和双边沿中断，使用状态表进行AB×4解码。当前：

```c
FEATURE_BALANCE_ENCODER_CAPTURE = 1
BALANCE_STEPPER_COMMAND_STEPS_PER_REV = 3200
BALANCE_ENCODER_COUNTS_PER_REV = 4096
BALANCE_ENCODER_DIRECTION_SIGN = 1
BALANCE_ENCODER_SPEED_SAMPLE_MS = 10
```

当前MT6816模块出厂默认使用AB模式，资料标注为1024线，AB×4后按4096计数/圈配置。仍必须通过
手动整圈验证：连续多次结果应接近±4096且重复一致；如果不是4096，不能用经验比例掩盖，应先确认接线
和实际解码方式。如果软件正向运动时ENC减少，将`BALANCE_ENCODER_DIRECTION_SIGN`改为-1。

10 ms M法测速使用带符号增量`n`：

```text
RPM = n × 100 × 60 / 4096
RPM_x10 = n × 600000 / (4096 × 10)
```

100μs/1ms ISR只在每10 ms锁存一次`n`，不执行除法；RPM换算放在OLED主循环显示路径中，避免
影响STEP脉冲时序。10 ms窗口下每1个计数约对应1.465 RPM，因此低速时R在相邻档位间跳动属于
M法量化现象，不等同于丢计数。例如实际约3.75 RPM时，10 ms内平均约2.56个计数，R可能在
约2.9和4.4 RPM之间变化。

采集验收流程：

```text
1. 断电接线；MT6816的VCC接3V3，GND接MSPM0 GND，禁止以5V供电后将输出直连PB6/PB7
2. 编码器A接PB6、B接PB7；PWM和Z在本阶段悬空不接
3. 如需在当前版本重做采集检查，上电进入平衡轴页面并保持Z:WAIT/REL；不要长按K1，以免进入标定或恢复
4. 手动同方向转动电机轴整整一圈，记录ENC；重复5次，应接近±4096
5. 根据正向运动符号修正DIRECTION_SIGN；若整圈不是4096，先检查AB接线、四倍频解码和模块规格
6. 停止状态观察30秒，ENC不得自行变化，IV不得持续增加
7. K2/K3低速正反运动；按3200 STEP/圈计算，200 STEP理论对应256 ENC，确认符号一致且ERR回到稳定小范围
8. 在计划最高速度和负载下连续往返，IV不增长且ERR不持续累积
```

编码器采集验收后已接入纯软件ZERO/LOW/HIGH标定，不增加机械限位开关，也不使用MT6816的
PWM或Z输出。AB是增量编码器，断电后绝对位置丢失，因此Flash只保存LOW/HIGH相对ZERO的偏移，
不能保存断电后的真实轴位置。每次重新上电仍必须把机构对准物理水平零点并长按K1确认一次；
确认后可直接恢复上次上下限，不需要重复走到两端。逻辑位置为：

```text
logical_position = raw_encoder_count - zero_raw_count
```

Flash记录位于主Flash最后一个1 KB sector：`0x0001FC00~0x0001FFFF`。链接时该sector由
`g_balanceCalibrationReservedSector`完整占用，运行代码和常量不得进入；记录包含Magic、版本、
结构长度、LOW/HIGH、4096 CPR、3200 STEP/rev、写入序号和CRC32。写入前电机必须停止，擦写期间
关闭中断，使用DriverLib FromRAM接口，写完立即读回校验。重新烧录固件会重置此记录，普通RST和
断电重启会保留。

首次标定或Flash无有效记录时，OLED显示`F:NA`或`F:BAD`、`Z:WAIT`。完整流程：

```text
1. 将机构放到物理水平零点；K1长按：当前位置设为逻辑0，并进入CAL:LOW
2. CAL状态下K2/K3短按：每次正/负微调20 STEP
3. 到达软件下限，停止后K1长按：记录LOW，进入CAL:HIGH
4. 移动到软件上限，停止后K1长按：记录HIGH、校验范围并立即写Flash
5. OLED显示`CAL:DONE F:OK`和`SAVE:OK`；K1长按退出标定
6. 标定中K3长按可取消；旧Flash记录尚未擦写时仍可在重新上电后恢复
```

已有有效记录时，上电恢复流程：

```text
1. OLED显示F:OK、Z:WAIT和上次L/H；此时非CAL的STEP命令全部被拒绝
2. 手动把机构对准物理水平零点
3. K1长按确认：当前ENC设为逻辑0，恢复Flash中的L/H并进入HOLD/READY
4. 不会自动寻找挡块，也不会自动运动到水平；水平位置必须由人确认
```

主动重新完整标定：

```text
1. READY/HOLD状态K3长按：释放EN并显示K1L=NEW K3L=CANCEL
2. 把机构放到新的物理水平零点，K1长按后重新执行LOW/HIGH完整标定
3. 如果不想重标，再次K3长按取消；重新对准原零点后K1长按可恢复旧Flash限位
```

LOW和HIGH允许与编码器正负方向相反，程序会自动取两者的数值最小值和最大值。只有ZERO位于
LOW/HIGH之间且总行程不少于64个编码器计数，标定才会成功；否则显示`ERR:RANGE`。标定完成后，
100 us STEP调度前会检查编码器逻辑位置：到达数值上限后只允许负向返回，到达数值下限后只允许
正向返回。Flash写入失败时OLED显示`ERR:FLASH RAM=OK`：本次上电的RAM限位仍可使用，但下次上电
必须重新完整标定。

旧的闭环`LOW→HIGH→ZERO`安全行程函数仍保留在底层，但当前OLED按键入口已改为连续轨迹测试。READY
状态长按K1后，控制器先闭环走到测试下端，然后以1秒为完整周期持续执行平滑
`LOW60%→HIGH60%→LOW60%`。测试上下端分别取逻辑ZERO到已标定LOW/HIGH距离的60%，并继续受位置
闭环安全边距和100 us软件限位保护。轨迹使用两段三次平滑曲线，端点速度为0，避免直接切换端点
产生过大的速度突变。K1或K3长按均可取消，取消后立即保持当前位置，不自动回零。

该模式是执行机构带宽测试，不是小球平衡控制。它只生成规定的目标轨迹，位置环仍保持当前
40~200 STEP/s限制；若机构无法在1秒内跟随，程序不会偷偷提高速度，而是在OLED上通过`E`和`M`
显示当前位置误差和本次运行最大误差。OLED的`C`为已完成周期数，`P/T/R`分别为实际编码器位置、
轨迹目标和当前STEP频率。只有`P`能稳定跟随`T`、`M`可接受且没有NOENC/FOLLOW/DIR/LIMIT故障，才
说明当前执行层具备下一阶段小球外环的基本能力。

位置控制与保护位于`balance_position_control.c/.h`，20 ms执行一次，100 us ISR仍只负责STEP边沿和
最后的软件限位拦截。故障均立即停止、保持EN并锁存，不能自动重试：

```text
NOENC：已累计发送32个STEP但编码器计数始终没有变化；覆盖编码器断线和完全堵转
FOLLOW：STEP理论位移与编码器实际位移相差超过64 count并持续200 ms；覆盖部分卡滞和持续失步
DIR：STEP方向与编码器变化方向相反并持续100 ms
TIME：按目标距离计算的动作总超时
LIMIT：闭环动作意外触发100 us软件限位
```

静止时，普通增量式AB编码器没有可用于判断“已断线”的主动信息，因此程序不能可靠检测静止断线；
`NOENC`只能在发出运动命令后判定。发生任一`POS FAULT`后，OLED显示目标、位置误差和跟随误差，
必须长按K3人工清除。复位只回到等待状态，绝不恢复或重发出错动作。K2/K3单次闭环测试和自动
LOW/HIGH/ZERO测试都使用同一控制器与同一保护链路。

首轮实机验收顺序：

```text
1. 空载、机构位于中间、保证可立即断电；上电对准物理零点并恢复Flash限位
2. K2短按：观察POSCTRL:RUN→SET，最终|E|≤4且进入HOLD；记录P、T、E、FE、R
3. K3短按返回；连续执行正/负各5次，确认无持续残差、无误报故障
4. K1长按启动连续往复，先不放小球，连续运行至少10个周期；确认C递增、P跟随T并记录最大误差M
5. K1长按取消，确认立即停止并保持当前位置；当前阶段不要用往复运动是否能稳球作为验收条件
6. 在远离限位的中间位置做NOENC保护测试：受控阻止编码器变化，约32 STEP内应停车并显示F:NOENC
7. 故障后普通按键不得重新运动；K3长按清故障后仍保持，必须重新按K2/K3才启动
```

不要在靠近机械端点时通过拔线验证NOENC；编码器失效时软件位置与限位都不再可信。若正常空载也出现
NOENC/FOLLOW，不应直接关闭保护，应先记录OLED的E、FE、R和实际动作，再调整门限或检查联轴器。

软件限位不能阻止断电、释放EN或外力造成的机械运动，也不能在编码器、联轴器或程序失效时提供
最后一道硬件保护。因此LOW/HIGH必须标在机械挡块以内并预留安全距离；它是当前快速落地方案，
不是硬件安全限位。上电后未确认ZERO且不在CAL页面时，STEP运动默认被拒绝；必须先确认物理零点
并恢复Flash限位，或完成首次/重新ZERO/LOW/HIGH标定。软件限位和编码器故障检测都不是机械安全
限位的替代品；首轮闭环验收必须低速、空载并保证可以立即断电。

### 15.4 K230毫米位置与静止小球PD

固定相机的像素到物理距离换算归K230负责，下位机不再保存`origin_px/pixels_per_cm`。当前接收
`@B,seq,time,valid,state,pos,pred,v,conf,measured*CS\n`ASCII行，`pos`为相对O点的毫米位置，题目目标
统一为0、+50、-50mm。`balance_ball_control.c/.h`
实现最小外环：

```text
error_mm = target_mm - position_mm
velocity_mm_s = 坐标差分低通
offset_count = Kp * error_mm - Kd * velocity_mm_s
actuator_target = 水平逻辑0 + 限幅/限速后的offset_count
```

外环不直接发STEP，而是使用`BalancePositionControl_StartTracking/SetTrackingTarget`，因此编码器跟随、
堵转/断线、方向错误和软件限位仍由原位置内环统一保护。当前没有I项，避免初次调试时积分饱和。

控制不会上电自动启动。BALL页面：

```text
K2短按：请求目标O=0mm的静止PD
K3短按或长按：退出PD并限制变化率返回水平
K2长按：全局急停，立即停止步进
```

真正进入`ACT`还要求ZERO和LOW/HIGH有效、无位置环故障、没有标定/往复测试占用执行器、置信度达到
门限并连续收到3帧合法位置。超过150ms没有有效位置时不再使用旧数据并回水平；超过400ms显示
`LOST`。单帧跳变超过60mm会被拒绝。初始外环只允许使用水平两侧可用行程的15%，同时上限为
64个编码器计数，每20ms目标最多改变4 count。

OLED BALL页面：

```text
P：K230当前位置，mm
T：MSPM0任务目标，mm
E：T-P，mm
V：滤波后球速，mm/s
U：当前步进位置偏移，encoder count
状态：OFF/AXIS/VIS/ACT/ZERO/LOST/FLT
```

首次实机只能把小球放在O点附近，并保证可以立即K3退出或K2长按急停。若误差增大时水管倾斜方向
明显把球推得更远，应停止测试并只修改`BALANCE_BALL_PD_TILT_SIGN`，不能先增大Kp。方向确认后再从
当前保守Kp/Kd开始调试。
