## 1. 文档目标、状态口径与最终边界

本文的目标不是继续扩展底层架构，而是完成以下有限工作后冻结P2～P6：

```text
排除构建与K2页面异常
→ 完整验收P6.2航向和转角
→ 实现并验收P6.3定距航向动作
→ 正式比赛任务全部迁移到新版动作
→ 全流程回归
→ 冻结P2～P6
```

状态标记统一如下：

| 标记 | 含义 |
|---|---|
| 已实车验收 | 源码存在，并已有明确实车结果支持 |
| 源码已实现，未完整验收 | 代码路径存在，但尚未完成规定测试矩阵 |
| 尚未实现 | 当前源码没有对应动作、状态或接口 |
| 后续计划 | 仅在本文中设计，尚未写入源码 |
| 已冻结 | 原则上不再改算法和标定参数，只允许修复明确缺陷 |

P6完成后的统一控制链目标为：

```text
MissionManager
→ MotionAction
→ CarController（唯一正常运动仲裁点）
→ P5 FOLLOW / DRIVE_HEADING / TURN_TO_YAW / DRIVE_DISTANCE_HEADING
→ 左右normalized命令（-1000～1000）
→ P4 MotorControl双轮速度闭环
→ Motor_SetSpeed
→ 硬件PWM与方向GPIO
→ 编码器与IMU反馈
```

安全链始终高于普通动作：

```text
K2软件急停 / heartbeat watchdog / SafetyHold
/ WheelSpeedEstimator错误 / MotorControl错误 / IMU无效 / 动作超时
→ 禁止普通控制目标
→ normalized目标0/0
→ 清PI及动作临时状态
→ Motor_Stop
→ 硬件PWM强制低
```

冻结后的地图和流程变化应只修改 `mission_library.c/.h` 中的任务数组、动作参数和注册项，不再修改P2～P6控制器算法。

## 2. 当前版本真实状态

### 2.1 P2：硬件PWM

状态：**已完成、已实车验收、已冻结**。

当前事实：

- `FEATURE_HW_MOTOR_PWM=1`；
- `Motor_SetSpeed()`统一处理方向GPIO和PWM占空比；
- `Motor_Stop()`在临界区内将两路PWM强制为低并清方向；
- 左右方向、上电不误转、软件急停、硬件PWM和软件PWM回退均已有实车结果；
- 软件PWM代码仍由功能开关保留，仅用于开发回退，正式比赛不启用。

后续边界：不修改TIMG8通道、20 kHz PWM、方向反相、停车时序或SysConfig引脚。

### 2.2 P3：编码器、轮速和里程

状态：**已完成、已实车验收、已冻结；尚未接入距离动作**。

当前标定：

```c
encoder_ppr_x2 = 734U;
wheel_diameter_cm = 6.5f;
wheel_track_cm = 11.25f;
left_encoder_direction = -1;
right_encoder_direction = 1;
```

当前解码与方向约定：

- ISR只在左右ENCA双边沿进入，读取ENCB判断方向，属于ENCA双边沿×2解码；
- `Encoder_GetAndClearPulseDeltas()`原子读清并保留符号；
- 前进时左右delta、累计脉冲和速度均为正；后退时均为负；
- 编码器delta的唯一消费者是 `WheelSpeedEstimator_Update()`。

计算关系：

```text
distance_per_pulse = π × wheel_diameter_cm / encoder_ppr_x2
raw_speed_cmps = delta_pulse × distance_per_pulse × 1000 / elapsed_ms
left/right_distance = total_pulse × distance_per_pulse
center_distance = (left_distance + right_distance) / 2
```

轮速使用 `alpha=0.35` 的IIR：

```text
filtered = previous + 0.35 × (raw - previous)
```

当前可直接复用的接口为：

```c
const volatile WheelSpeedEstimatorRuntime *WheelSpeedEstimator_GetRuntime(void);
```

其中已包含左右delta、左右total、左右累计距离、中心累计距离、原始/滤波速度、`valid`、`stale`、`overflow` 和 `error_flags`。P6.3动作开始时只保存 `center_distance_cm` 基准，不清零真实累计值。

### 2.3 P4：双轮速度闭环

状态：**已完成、30 cm/s实车验收通过、已冻结**。

当前开关：

```c
FEATURE_WHEEL_SPEED_CONTROL = 1;
FEATURE_MOTOR_CONTROL_FAST_SETTLING = 1;
FEATURE_WHEEL_SPEED_TEST = 0;
```

命令映射：

```text
target_speed_cmps = normalized_command / 1000 × 60
```

当前参数：

| 参数 | 当前值 |
|---|---:|
| 最大映射速度 | 60 cm/s |
| 左右加速侧Kp | 4.0 |
| 左右超速侧Kp | 5.0 |
| 左右Ki | 1.0 |
| 左右前馈系数 | 0.5 |
| 积分限幅 | 300 |
| 积分释放倍率 | 4 |
| 最大加速度 | 60 cm/s² |
| 最大减速度 | 120 cm/s² |
| 目标刷新超时 | 100 ms |

实际公式：

```text
error = ramped_target_speed - measured_filtered_speed
feedforward = ramped_target / 60 × 1000 × feedforward_gain
output = feedforward + kp_used × error + ki × integral
```

当前具备左右独立PI、前馈、目标斜坡、输出限幅、anti-windup、超速侧增益、误差换向积分释放、安全换向、零目标停车、估算器错误停车、目标刷新超时和错误锁存。功能开启时，普通业务最终由 `MotorControl` 唯一调用 `Motor_SetSpeed()`；`CarController`中的直接调用只属于编译期关闭P4后的开环回退分支。

### 2.4 P5：七路稳定循迹

状态：**已完成、已实车验收、效果稳定、正式冻结**。

当前开关与参数：

```c
FEATURE_LINE_CONTROL_V2 = 1;
base_command = 220;
error_filter_alpha = 0.35f;
derivative_filter_alpha = 0.20f;
kp = 0.35f;
kd = 0.010f;
max_correction = 120;
min_running_command = 50;
lost_turn_command = 280;
lost_search_max_ms = 2000U;
```

普通FOLLOW：

```text
七路数字传感器
→ 对称加权误差
→ error IIR
→ 基于真实elapsed的微分和微分IIR
→ correction = Kp × filtered_error + Kd × filtered_derivative
→ left = 220 + correction
→ right = 220 - correction
```

普通命令约为100～340，对应P4目标约6.0～20.4 cm/s。普通FOLLOW不允许反转，0到最低稳定命令之间直接归零。

当前全白恢复：

```text
S1有效且S7无效 → 记录LEFT
S7有效且S1无效 → 记录RIGHT
全白且方向有效 → 0/280或280/0搜索
重新看到任意黑线 → 当前周期返回FOLLOW并重新处理当前图案
持续全白达到2000 ms → STOP/RECOVER_TIMEOUT
全白但无方向 → STOP/NO_DIRECTION
```

后续不再加入复杂TrackStateEstimator、置信度、CROSS分类、动态速度调度、复杂REACQUIRE或弯道分类。

## 3. 最终总体架构

### 3.1 普通循迹

```text
七路传感器
→ P5误差滤波与PD
→ 左右normalized目标
→ P4双轮速度闭环
→ Motor_SetSpeed
→ 硬件PWM
→ 编码器反馈
```

### 3.2 航向直行

```text
目标Yaw
→ Angle_Normalize180(target-current)
→ HeadingControl（P + 实测-gyro_z微分反馈）
→ 基础normalized命令 ± correction
→ P4双轮速度闭环
→ 硬件PWM
```

### 3.3 精准转角

```text
相对角度
→ target_yaw = Normalize(current_yaw + relative_angle)
→ FAST双轮反转
→ SLOW双轮反转
→ 角度容差内0/0
→ 角速度和时间共同停稳
→ DONE
```

### 3.4 指定距离直行

```text
目标有符号距离
→ 保存center_distance起点
→ 计算travelled与remaining
→ 远距离正常命令
→ 进入slow zone降低命令
→ HeadingControl保持锁存Yaw
→ 距离容差内0/0
→ 左右轮速和时间共同停稳
→ DONE
```

### 3.5 控制权和安全链

```text
急停/真实故障
> SafetyHold
> 避障临时接管
> TURN_TO_YAW
> DRIVE_DISTANCE_HEADING
> DRIVE_HEADING_TIME
> P5 FOLLOW/SEEK
> IDLE
```

任一20 ms周期只能有一个CarController run_mode提交普通运动目标。SafetyHold、急停、watchdog和错误状态可以直接阻止最终输出，但不得在另一个普通控制器中复制第二套安全状态机。

### 4.1 阶段A：构建与启动一致性确认

第一步不修改按键源码，先执行：

```text

→ 确认menu.c、oled_ui.c、app_features.h、car_controller.c重新编译
→ 核对输出文件时间戳和路径
→ J-Flash完整擦除
→ 烧录本次新镜像
→ 上电静止完成IMU校准
→ 分别从HOME与HEAD执行TASK 3
```

判断分支：

#### A1：完整重编译后问题消失

- 结论为旧目标文件、增量编译或烧录镜像不一致；
- 不修改 `key.c`、`menu.c` 或任务启动逻辑；
- 记录正确构建和烧录文件路径，进入阶段B。

#### A2：完整重编译后问题仍存在

按顺序只读/诊断：

1. `Key_Update_20ms()`是否生成一次 `KEY2_SHORT`；
2. `Key_GetEvent()`是否只消费一次；
3. `Menu_HandleKeyEvent()`进入时的真实 `g_oledPage` 和 `CarState`；
4. HOME、DRIVE、LINE、HEAD、OBS是否都进入普通K2分支；
5. `MissionManager_Start()`返回值、当前definition和MissionStatus；
6. 页面切换是否改变任务选择或CarState；
7. PARAM和云台调试页是否截获K2；
8. OLED与Runtime读取是否存在副作用；
9. 只有确认真实缺陷后才做最小修复。

通过条件：HOME与HEAD在相同READY状态下，K2短按均能把任务从READY切换为RUN，并启动同一个动作。

### 4.2 阶段B：完整验收P6.2

实施顺序：

1. 先确认左右命令符号，不调Kp/Kd；
2. 再确认+90°和-90°；
3. 再测试±170°；
4. 单独规定180°方向；
5. 验证FAST→SLOW→停稳→DONE；
6. 验证超时、IMU无效和DONE保持停车；
7. 最后验证DRIVE_HEADING左右扰动；
8. 只有方向正确后才允许一次只调一类参数。

调参纪律：

- 转向方向反了：只修正一次统一的转向符号，不动P4、IMU axis sign或多个模块取负；
- 启动冲击或FAST速度问题：只调 `turn_speed`；
- 接近目标仍冲过：先调SLOW命令或FAST→SLOW阈值；
- 5°附近反复启停：再考虑增加 `settle_exit_deg` 迟滞；
- 停稳后仍不DONE：检查gyro阈值和稳定时间；
- DRIVE_HEADING修正方向正确但摆动：一次只调Kp或Kd，先Kp后Kd；
- 方向未确认前禁止调整HeadingControl增益。

P6.2通过后冻结 `heading_control.c/.h`、TURN_TO_YAW逻辑和对应参数；P6.3只能调用这些能力，不能顺手重调。

### 4.3 阶段C：实现P6.3最小距离动作

只实现：

```text
DRIVE_DISTANCE_HEADING(distance_cm, normalized_command, timeout_ms)
```

不实现曲线轨迹、S曲线、MPC、多段路径规划或位置PID。

#### 动作开始

1. 检查WheelSpeedEstimator `valid=1`、`stale=0`、`error_flags=0`；
2. 检查 `Imu_IsReady()`；
3. 记录 `start_left_distance_cm`、`start_right_distance_cm` 和 `start_center_distance_cm`；
4. 正距离表示前进，负距离表示后退；
5. `normalized_command`定义为非负幅值，实际方向由distance符号产生，避免双重符号矛盾；
6. 锁存当前Yaw为目标Yaw；
7. Reset并Enable HeadingControl，但不调用 `Imu_ResetYaw()`；
8. 清距离动作的elapsed、settle、result和错误状态；
9. 进入新的互斥run_mode。

#### 动作运行

```text
travelled = current_center_distance - start_center_distance
remaining = target_distance - travelled
direction = sign(target_distance)
```

远距离使用 `direction × normal_command`；进入slow zone后使用 `direction × slow_command`；进入容差后输出0/0并等待轮速停稳。

HeadingControl correction继续使用目标Yaw与当前Yaw，并形成：

```text
left_command  = base_command + correction
right_command = base_command - correction
```

必须对correction做动态限幅，保证普通定距直行中两轮不反转，并避免某侧落入0到最低稳定命令之间。倒车修正方向必须通过实车左右扰动单独验证，不能按名称猜测。

#### 接近终点和越界策略

采用两段速度：

```text
|remaining| > slow_distance_cm  → normal command
distance_tolerance < |remaining| ≤ slow_distance_cm → slow command
|remaining| ≤ distance_tolerance → 0/0并进入SETTLE
```

最小版本不自动反向修正越界，避免在终点附近前后抖动。若越过目标且误差超出容差，应保持0/0并锁存overshoot诊断，最终由超时或专门失败结果结束；先通过slow zone标定减少越界。

#### 完成条件

同时满足：

```text
|remaining| ≤ distance_tolerance_cm
|left_speed| ≤ settle_speed_threshold
|right_speed| ≤ settle_speed_threshold
持续settle_time_ms
```

才返回SUCCESS。

#### 失败条件

至少包括：

- ENCODER_INVALID；
- IMU_INVALID；
- TIMEOUT；
- CANCELLED；
- 可选的OVERSHOOT/INVALID_ARGUMENT诊断，但不扩展复杂故障体系。

失败、取消、急停、SafetyHold、暂停或超时后必须持续0/0，清HeadingControl和距离动作临时状态，不自动恢复旧PWM或旧目标。

#### 暂停和恢复

当前 `MissionManager_Pause()` 会Stop并 `MotionAction_Init()`，Resume会从头重启当前动作。该语义若直接用于定距，会重新执行完整距离。阶段C必须明确处理：

- 推荐的最小方案是为距离动作保存 `remaining_distance_cm`；
- Pause时保存剩余距离并停车；
- Resume时以当前位置作为新基准，仅执行保存的剩余距离，同时保留原目标Yaw；
- 若不实现该能力，则比赛Profile必须禁止对定距动作执行Resume，并把Pause定义为取消，需要重新启动任务；
- 不允许在语义未定义时默认从头再跑完整距离。

### 4.4 阶段D：正式任务全面迁移

正式比赛任务只保留一种主路径：

```text
FOLLOW                → P5 V2
指定角度转向          → TURN_TO_YAW
指定距离直行          → DRIVE_DISTANCE_HEADING
只要求定向走固定时间  → DRIVE_HEADING_TIME

```

旧动作可以保留在Development Profile作为硬件回退，但Competition Profile不得继续调用旧单轮90°动作或以时间代替明确距离要求。

## 5. P6.2与P6.3状态机设计

### 5.1 TURN_TO_YAW验收目标状态机

当前源码按阈值分支实现，验收时按以下逻辑观察：

```text
IDLE
  ↓ Start(relative_angle)
FAST（|error|>12°，±130）
  ↓ |error|≤12°
SLOW（5°<|error|≤12°，±65）
  ↓ |error|≤5°
SETTLE（0/0，检查gyro和100 ms）
  ├─ 稳定满足 → DONE
  ├─ 误差重新增大 → SLOW/FAST
  ├─ IMU无效 → 0/0，宽限后IMU_INVALID
  └─ elapsed≥4000 ms → TIMEOUT
```

若增加7°迟滞，必须集中配置，且只改变SETTLE退出阈值，不改变进入5°阈值。

### 5.2 DRIVE_HEADING状态机

```text
IDLE
  ↓ Start(target_yaw, duration)
RUN（base=100，Heading correction±30）
  ├─ duration完成 → 0/0 → DONE
  ├─ IMU短时无效 → 立即0/0并累计宽限
  ├─ IMU持续无效 → IMU_INVALID
  └─ action timeout → TIMEOUT
```

### 5.3 DRIVE_DISTANCE_HEADING建议状态机

```text
IDLE
  ↓ 参数/传感器检查成功
CRUISE
  ↓ |remaining|≤slow_distance
SLOW
  ↓ |remaining|≤tolerance
SETTLE（0/0）
  ├─ 两轮速度低且持续settle_time → DONE
  ├─ 编码器异常 → ENCODER_INVALID
  ├─ IMU异常 → IMU_INVALID
  ├─ 超时 → TIMEOUT
  ├─ 取消/急停 → CANCELLED
  └─ 越界超容差 → 保持0/0并锁存诊断
```

## 6. P6.3建议接口

当前工程已经有统一的 `MotionAction_Start()`、`MotionAction_Update_20ms()` 和 `MotionAction_Cancel()`，不应创建第二套动作执行器。

建议新增的数据类型：

```c
typedef enum {
    DRIVE_DISTANCE_IDLE = 0,
    DRIVE_DISTANCE_RUNNING,
    DRIVE_DISTANCE_DONE,
    DRIVE_DISTANCE_ENCODER_INVALID,
    DRIVE_DISTANCE_IMU_INVALID,
    DRIVE_DISTANCE_TIMEOUT,
    DRIVE_DISTANCE_CANCELLED
} DriveDistanceResult;
```

建议CarController入口：

```c
bool CarController_StartDriveDistanceHeading(
    float distance_cm,
    int16_t normalized_command,
    uint32_t timeout_ms);

DriveDistanceResult CarController_GetDriveDistanceResult(void);
```

更新函数不建议公开成第二条调度链。应在 `CarController_Update_20ms()` 的新run_mode分支中调用内部函数：

```c
static void handle_drive_distance_heading(uint32_t elapsed_ms);
```

若项目确实要求公开命名，可提供只由 `CarController_Update_20ms()` 调用的薄封装：

```c
void CarController_UpdateDriveDistanceHeading(uint32_t elapsed_ms);
```

但不得由App、MotionAction和CarController多处重复调用。

MotionAction继续复用现有接口：

```c
bool MotionAction_Start(const MotionAction *action);
MotionActionResult MotionAction_Update_20ms(uint32_t elapsed_ms);
void MotionAction_Cancel(void);
```

需要扩展：

```c
MOTION_ACTION_DRIVE_DISTANCE_HEADING

params.drive_distance_heading.distance_cm       // 有符号cm
params.drive_distance_heading.normalized_command // 非负幅值1..1000
```

timeout沿用 `MotionAction.timeout_ms`，表示从控制器真正启动后到DONE的最大真实elapsed。IMU启动等待时间应继续单独记录，避免未就绪等待吞掉全部动作时间。

取消语义：立即0/0，结果CANCELLED，清临时状态，不改变IMU bias，不清编码器真实累计值。

现象判据：

- 符号反了：扰动后yaw error绝对值持续增大，或目标正角却稳定向相反方向转；
- Kp过大：低频左右往返且不快速衰减；
- Kd过大：输出对gyro噪声敏感、动作断续或回正明显迟钝；
- SLOW过低：进入12°后停滞并最终TIMEOUT；
- SETTLE条件过严：已经静止但stable_ms反复归零；
- SETTLE条件过松：车仍明显转动就DONE；
- 距离slow zone过晚：高速进入容差并明显越界；
- 低速量化问题：M10呈脉冲式跳变，终点SETTLE反复开始和清零。

## 11. 风险与回退

### 11.1 主要风险

1. Debug目录被纳入版本管理，旧 `.o/.d/makefile` 与增量编译可能造成源码和镜像不一致；
2. J-Flash工程可能继续引用旧输出文件；
3. TURN_TO_YAW和Heading correction符号可能在左右方向不对称；
4. `Angle_Normalize180()`在精确180°返回-180°，任务必须明确+180/-180方向；
5. 当前TURN_TO_YAW无独立SETTLE退出迟滞；
6. 低速双轮反转或距离slow command可能低于实车稳定运行能力；
7. 20 ms编码器量化可能影响终点停稳；
8. Heading correction叠加后某侧命令可能过低或改变符号；
9. 当前Pause/Resume会重启当前动作，直接用于定距会重复完整距离；
10. MAP-A/B仍依赖旧90°动作和旧90°事件；
11. 避障DRIVE_OUT仍按1400 ms完成，不保证实际距离；
12. 避障接管后若没有正确Reapply，原Mission会冻结或目标丢失；
13. OLED当前直接读取多个模块Runtime，不完全符合“统一只读Snapshot”的理想边界；
14. 硬件WWDT未配置，当前只有软件heartbeat停车覆盖。

### 11.2 回退策略

- 每个阶段独立提交：A构建证据、B P6.2、C P6.3、D任务迁移、E冻结；
- P6.3失败时退回P6.2稳定标签，不修改P2～P5；
- 保留旧TURN_90、DRIVE_HEADING_TIME和Development测试任务作为回退；
- 保留软件PWM编译分支，但Competition始终使用硬件PWM；
- 保留 `FEATURE_*` 开关，禁止在Competition同时启用新旧业务链；
- 正式比赛前建立最终冻结commit和tag，并记录J-Flash镜像哈希/时间戳；
- 只有明确底层缺陷才从冻结标签分支修复，修复后重新执行相关回归矩阵。

## 12. 最终冻结条件

只有同时满足以下条件，才能宣布底层运控冻结：

1. P2硬件PWM、方向和停车继续稳定；
2. P3左右速度、累计脉冲和里程方向正确；
3. P4双轮速度闭环无回归；
4. P5保持当前循迹和全白恢复水平；
5. HOME和HEAD启动行为一致；
6. +90°和-90°均完成；
7. ±170°和明确方向的180°完成；
8. TURN_TO_YAW超时锁存停车；
9. DONE后不重新启动；
10. DRIVE_HEADING左右修正方向正确；
11. DRIVE_HEADING 3 s不持续蛇形；
12. DRIVE_DISTANCE_HEADING完成前进和后退；
13. 20/50/100 cm误差满足比赛需求；
14. 定距过程中航向保持有效；
15. 编码器和IMU异常均能停车；
16. 暂停、取消、急停和超时后无旧目标恢复；
17. MAP-A/B/C全部迁移到允许的新动作；
18. Competition Profile不再注册开发任务，不再调用旧TURN_90；
19. 避障接管和恢复通过回归；
20. K2急停、K3复位、SafetyHold和watchdog无回归；

## 13. 冻结后的工作边界

冻结后允许：

- 修改 `mission_library.c/.h` 的静态动作数组；
- 调整地图动作顺序、目标距离、目标角度和动作timeout；
- 添加新的比赛地图任务注册项；
- 修改与赛道流程直接相关但不改变底层算法的障碍策略参数。

冻结后禁止：

- 重调P2～P5和P6.1参数；
- 重写MotorControl、LineController、IMU或HeadingControl；
- 新建另一套电机、速度、航向或距离输出链；
- 引入完整P7 SafetySupervisor、FaultManager重构；
- 实施Flash双槽持久化、复杂TrackStateEstimator、动态速度规划、复杂轨迹规划、卡尔曼/磁力计/四元数、RTOS迁移或大规模目录重构。

不得删除现有软件急停、SafetyHold、watchdog骨架、FaultCode、RuntimeSnapshot、OLED故障显示、missed/drop/overrun统计、编码器错误停车、IMU错误停车、TURN_TO_YAW超时和丢线超时。

## 15. 当前源码与现有文档不一致清单

1. 《工程文档》仍描述已经删除的TEST-YH、REACQUIRE_LINE及若干不存在的ACTION宏；当前源码只有独立TEST-TURN和TEST-HEAD；
2. 《工程文档》部分段落仍把TURN_TO_YAW描述为单轮转向，当前源码已经是双轮反向；
3. 《工程文档》示例写 `APP_PROFILE_COMPETITION`，当前源码实际为 `APP_PROFILE_DEVELOPMENT`；
4. 现有P6.2文档把FAST/SLOW/SETTLE写成显式状态机并提到SETTLE退出7°，当前源码没有显式状态枚举，也没有7°参数；
5. `motion_types.h`中的多个 `speed_override` 和 `min_turn_ms` 字段当前没有被动作执行链使用；
6. `DRIVE_HEADING_TIME`当前锁定的是动作参数给定的绝对Yaw，TEST-HEAD传入0°；旧文档中“进入动作时自动锁定当前Yaw”的描述不适用于当前通用接口；
7. OLED当前虽然不改变控制、不清编码器，但直接读取多个模块Runtime，并非只读取 `RuntimeSnapshot`；
8. 当前普通OLED循环源码已改为HOME→DRIVE→LINE→HEAD→OBS，但相关旧文档仍记录十页历史循环；该OLED改动尚需完整Clean/Rebuild和实车确认；
9. 正式MAP-A/B仍使用旧TURN_LEFT_90/RIGHT_90，尚未全面迁移到TURN_TO_YAW；
10. 避障转向已使用TURN_TO_YAW，但DRIVE_OUT仍使用按时间的DRIVE_HEADING；
11. 当前Competition Profile只隐藏开发任务，但MAP数组本身尚未满足“全部使用新版角度和距离动作”；
12. watchdog当前是软件heartbeat骨架，硬件WWDT开关为0且开启会触发编译错误，不能写成硬件watchdog已经完成。
